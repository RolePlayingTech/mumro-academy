# Internal development: proportional merge gates (owner decision 2026-10-30)

Scope: MUMRO Academy. This repository is under active internal development; code merged to GitHub `main` is **not** an acceptance claim or an authorization to publish, deploy, migrate, connect real providers, bill, or change a running service. Existing OVH/Hetzner live services and credentials may still be real, regardless of product launch status.

## Decision model
1. Prefer small, reversible PRs and make forward progress. **Full CI, E2E, real-provider pilot and a complete environment are not blanket prerequisites to merging internal-only work.** GitHub Actions remain disabled where so configured; never launch or rerun them merely for a merge.
2. For docs, fixtures, isolated dormant components (feature flag OFF, no existing import/runtime or SQL side effect), a diff review, dependency check and a clear rollback may suffice. Focused tests are useful, not automatically mandatory if unavailable.
3. For executable code integrated into active flows, perform the cheapest relevant checks possible and inspect key negative paths. For auth/tenant, migrations, financial/audit logic, secrets, provider publication, asynchronous jobs, SQL isolation or release infrastructure, require concrete reasoned review; focused tests whenever feasible. No fabricated PASS. `NOT RUN` must list missing coverage and risk.
4. **Do not merge knowingly harmful defects**: tenant crossing, leak of tokens/passwords, unintended external action or duplicate publication, data loss/corruption, invalid accounting/audit evidence, unsafe migration or an identified high-severity exploit. A genuine P0/P1 review finding with plausible impact must be fixed or fully fenced from all active execution paths before merge; do not relabel a known FAIL as absent test infrastructure.
5. An external-provider contract that is not yet verified (e.g. Zernio OAuth grant attribution or LinkedIn organization authority) **does not itself block merging a dormant, fail-closed integration foundation**. Keep unverified activation/publishing OFF and record a follow-up before any live use. Do not use synthetic verification as real authorization.
6. Each merge decision must record PR number, exact HEAD SHA, affected area, what was actually tested/reviewed, `PASS`/`FAIL`/`NOT RUN`, known issues, why the change is safe *in its current disabled/internal scope*, and next steps. The person merging accepts scope-specific documented risk, not an automatic global waiver. Merge stacked PRs in dependency order; never obscure failing checks.
7. **No deployment, restart, migrations on existing instances, DNS/egress/network changes, live OAuth/publishing, provider billing, changing secrets, real accounting/tax operation or public release without separate explicit operation-specific owner authorization.** No destructively testing real data. Existing Hetzner isolation and lock boundaries remain in force when tests do run.
8. Reintroduce full regression, documented provider grant/identity proof, adversarial tests, production smoke and operational readiness gates **before external/commercial customer launch**. Track these tasks in existing GitHub Issues/PRs; do not create a second backlog. Do not claim the product is launch-ready because code was merged.

This decision supersedes older stricter **pre-merge full-CI-only** language in project agent instructions for internal-only integration. It does **not** supersede security invariants or release authorization boundaries.
